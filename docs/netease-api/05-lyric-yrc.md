# 网易云逐字歌词（yrc）实测

> 2026-11-18 实测。样本 10 首（4 首有 yrc）。验证脚本 `tmp/yrc/YrcProbe.cs`（临时 file-based app，未转正式探针）：
> `dotnet run tmp/yrc/YrcProbe.cs -- <songId> [更多 id...]`。
> 解析状态机移植自 [WXRIW/Lyricify-Lyrics-Helper](https://github.com/WXRIW/Lyricify-Lyrics-Helper) `YrcParser.ParseOnlyLyrics`（Apache-2.0）。

## 1. 只有 `lyric/v1` + 加密通道才给 yrc

| 通道 | 请求 | 返回 yrc？ |
|---|---|---|
| 明文 `GET /api/song/lyric` | `lv/kv/tv=-1` | ❌（连 `yrc` 字段都没有） |
| 明文 `GET /api/song/lyric/v1` | `cp=false&lv/kv/tv/rv/yv/ytv/yrv=-1` | ❌（keys 只有 `lrc/klyric/tlyric/romalrc`） |
| **weapi `POST /weapi/song/lyric`** | `os=pc&lv/kv/tv=-1` | ❌（实测 6 首全 0） |
| **weapi `POST /weapi/song/lyric/v1`** | 见下 | ✅ |

payload：

```json
{"id":<id>,"cp":false,"os":"pc","lv":-1,"kv":-1,"tv":-1,"rv":-1,"yv":-1,"ytv":-1,"yrv":-1,"csrf_token":""}
```

⚠ 这条与项目现有双通道架构直接冲突：**明文回落拿不到 yrc**。一旦 `_wafBlocked` 置位，逐字就没了，只能回落行级 LRC。
2026-11-18 本机 weapi 歌词端点**可用**（`code=200`），未触发既有的"空 body"风控特征。

## 2. 格式

```
{"t":0,"c":[{"tx":"作词: "},{"tx":"唐恬"}]}          ← 头部 credits，JSON 行，可整行跳过
[33100,8050](33100,400,0)深(33500,230,0)海(33730,270,0)中...
[42170,11850](42170,170,0)我...
```

- 行头 **`[start,dur]` 两字段**（不是网上常见的 `[start,dur,0]` 三字段）。
- 字标签 `(start,dur,0)text`，第三字段恒 0。
- 行 `dur` = 到下一行开始的距离（含句尾停顿），与字末时间一致（±1ms）。

## 3. 切分规则（实测）

- **中文按字**：`我(28480,160) 带(28640,420) 着(29060,230)`
- **英文按词**：`You(204392,544) Are(204936,544) The(205480,544) Hero(206024,546)`（不是按字母）
- **标点、空格独立成字**，且空格常附在前一个字后面：`(30720,500,0)李 `、`(42070,440,0) `（纯空格字）
- **句尾长音由空格字承载**：实测 `(37820,3330,0) ` 3.3s、`(45470,3190,0) ` 3.19s，最长见过 18.3s
- **少量行是整行均分**（不是真逐字）：孤勇者 1/57 行、我记得 1/21、星辰大海 1/35。判据：行内所有字 `dur` 完全相等（±2ms）

## 4. 四个坑

1. **行头两字段**。按 `^\[(\d+),(\d+),\d+\]` 写正则会一行都匹配不上（实测 57 行全 miss）。
2. **`Trim()` 会吃掉行尾空格字**。那个空格正是句尾长音的载体，丢了会让高亮提前停在倒数第二个字上。
   正确做法：`TrimEnd('\r')` + `TrimStart()`，保留行尾空格。修前《笼》每行少 1 字（340 vs 373）。
3. **yrc 文本与 lrc 有差异**：标点全半角不同（`(YouAreTheHero)` vs `（YouAreTheHero）`）；
   和声/背景人声的括号会被剥掉（lrc `（为什么）` → yrc `为什么`）。
   ⇒ **文本取 lrc，时间轴取 yrc**，按行时间对齐合并；直接用 yrc 文本会丢括号。
4. **覆盖率不是 100%**。样本 10 首：孤勇者、笼、我记得、星辰大海 有；晴天、起风了（2 版）、
   罗刹海市、光亮、永不失联的爱、绝配 无。回落必须有。

| 笼 | 2057534370 | 35 | 373 | 0 | 0 | 3（和声括号被剥） |

## 6. 渲染侧提醒

- 每行第一个字的 `start` 等于行头 `start`，行内时间单调；**渲染只需按字推进一个游标**，不必每帧重排。
- 均分行与真逐字行混在一起，扫光速度会从"跟唱"突变为"匀速"——观感上能看出来，但属数据固有问题。
- 句尾长音（空格字）应让游标停在可见文本末端，不要把 3.3s 摊给最后一个可见字。

## 7. 生产接入（2026-11-18）

- `NetEaseApiClient.LyricWeapiAsync` 切到 `/weapi/song/lyric/v1`（带 `cp/os/lv.../yv/ytv/yrv`），
  `LyricResult.Yrc` 存原始 yrc；明文回落路径没有 yrc（保持空）。
- `LrcParser.Parse(original, translation, yrc)`：解析 yrc → 按行时间（±1000ms）贴到 LRC 行。
  **文本对齐**：忽略空白与全部括号后逐字符比较；对不上的行直接放弃（保留整行高亮）。
  不这么做会碰到两类差异：全半角括号、和声括号被剥（lrc「（为什么）」→ yrc「为什么」）。
  容差 300ms 时《我记得》只对上 12/21 行，放到 1000ms 后 16/21；文本匹配本身是强约束，不会贴错。
- 缓存格式升到 v3（多存 yrc），旧版本缓存直接作废重取（v2 是"字段在但值恒空"的那一版）。
- 渲染侧见 [karaoke-lyrics.md](../karaoke-lyrics.md)（`KaraokeText`，`--karaoke` / `--karaoke-real`）。
- 探针：`--yrc [songId...] [--after-search]`（`YrcProbe`）。实测四首合并 53/57、35/35、16/21、35/35 行，
  字级时间 0 个 `End<Start`。`--after-search` 先跑一次搜索再取词，复现真实 App 顺序（见下一节）。

### 另一份可参考的实现：Cloudy（AGPL-3.0，只看思路）

[nya-owo/cloudy](https://github.com/nya-owo/cloudy) `internal/lyrics/lyrics.go` 的 `parseYRC`/`Build`：

- **直接把 yrc 当主歌词源**，不与 lrc 做行文本匹配 —— 不会丢行，代价是显示文本用 yrc 版本（少几个括号）。
- 纯空格字**合并到前一个字的 Text**（时间丢弃），避免游标停在空白上。
- 没逐字的行用 `SpreadWords` 按字数均分，且只占行时长 85%（留出句尾停顿）。
- 整体均分的来源会被判为"不比行级好"而丢弃（`Uneven`）。

本项目选了"逐行对齐、失败回退"：现有 UI 一直显示 lrc 文本，换源会看到括号差异。
⚠ 它是 **AGPL-3.0**，与 GPL-3.0 项目不兼容（引入即要求整体 AGPL），只能参考算法、不能抄代码。

## 8. 上线当天踩的三个坑（2026-11-18）

现象：《孤勇者》播放时完全没有逐字效果，缓存文件里 `yrc` 长度为 0（但直接跑 `--yrc` 探针一切正常）。

### 8.1 `_wafBlocked` 是全局的，搜索会把它置位

`NetEaseApiClient` 里 `_wafBlocked` 的语义是"本进程有任意一个 weapi 被【代理出口】拦过"，
`SearchAsync` / `GetPlayUrlCoreAsync` 一旦碰到空 body 就把它设成 true，之后所有端点跳过加密通道。
歌词原来也吃这个判断 ⇒ **启动 → 搜歌（置位）→ 播歌** 这条最常见路径上，歌词永远走明文、永远没有 yrc。

修法：`GetLyricAsync` 不看 `_wafBlocked`，只维护歌词自己的两态
（代理不通 → 本进程改直连；直连也不通 → 这一首走明文）。回归探针必须带 `--after-search`。

### 8.2 `HttpClientHandler.Proxy = null` 不是"直连"

.NET 里 `Proxy = null` 的语义是**改用系统/环境变量代理**（`HTTP_PROXY`/`HTTPS_PROXY`），
而本机那两个环境变量指着的正是同一个被风控的出口 ⇒ 所谓"直连兜底"其实又走了一遍代理。
必须显式 `UseProxy = false`。实测同一请求：`Proxy=null` → `yrc` 0 字符；`UseProxy=false` → 9869 字符。

### 8.3 空 body 是按请求抽中的，且明文结果不能落缓存

同一首连跑三次大约有一次空响应（与加密字节级正确无关），所以：

- 同一通道**重试**比立刻换通道更有效：现在最多 4 次尝试（200/400/600ms 退避），跨代理/直连各试。
- 明文回落拿到的结果 **不写缓存**（`LyricResult.Cacheable = false`）：明文永远没有 yrc，
  一旦落盘，下次即使加密通道恢复也只会命中"没有逐字"的旧结果 —— 这首歌就永久失去逐字。
  `LyricViewModel.LoadAsync` 只缓存 `Cacheable` 的结果。

对应的渲染验证：`--karaoke-real [id]`（真实 yrc → LrcParser → detail 模板 → 像素统计），
不再只依赖合成假数据。
