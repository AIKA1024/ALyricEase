# 性能测量与结论（GPU / CPU）

从 `.workbuddy/memory/MEMORY.md` 外移（该文件有注入长度上限，只留结论与入口）。
Avalonia 框架层面的坑（事件类型、门控写法等）在 `docs/avalonia-tips.md`；内存设计审计在 `docs/memory-audit.md`。

## 一、怎么量 GPU

- 用 PDH 计数器 `\GPU Engine(*)\Utilization Percentage`：按 `pid_` 前缀过滤、**加总所有引擎**
  （3D / Copy / Compute / VideoDecode），并**丢弃第一个采样**（速率型计数器要两次收集才有值）。
  实现：`src/ALyricEase.Headless/GpuUsageSampler.cs`（P/Invoke `Pdh*`，实例结构体步长 24 字节）。
- 抓屏验证：`src/ALyricEase.Headless/ScreenCapture.cs`（GDI BitBlt + `DiffRatio`），用来判"某效果到底有没有真画出来"。
- ⚠ **GPU 计数器只在窗口可见且未被遮挡时才有值**。被遮挡时 DWM 不合成，读数恒 0 ——
  这种"数字很漂亮"的错误比崩溃更难查。探针必须 `Topmost = true`（会盖住桌面约两分钟）。
- 参考探针 `--np-gpu-real`（`src/ALyricEase.Headless/NowPlayingGpuProbe.cs`）：
  真 `TestMainWindow` + 真 `AppShell` + 真 `NowPlayingView` + 真 `PlayerViewModel`；
  网络不可用时封面注入合成位图、歌词直接灌进 `LyricViewModel`。同轮消融矩阵 + 抓屏像素验证。
  `ALY_NP_SIZE=WxH` 对齐用户实际窗口（填充率与面积成正比）。

## 二、结论：详情页 GPU 的大头是"在动"，不是"在画"

`AlbumCoverBackground` 的漂移动画（全屏色团横跨整窗移动，让合成器每帧重画整幅窗口）实测（1200x720）：

| 项 | 净代价 |
|---|---|
| 漂移本身 | **+7.53% GPU / +21% CPU** |
| 色团层**画出来** | 仅 **+1.77%** |
| 两个进度 RAF 循环 | ≈ **+0.25%** |

⇒ **代价与"看不看得见"无关，钱花在动上。**

根因：`NowPlayingOverlay` 在真实 `MainWindow.axaml` 里是**常驻**的（只靠 `RenderTransform` 移出窗外），
所以色团从启动起一直在动，哪怕详情页没打开。

修法：`AlbumCoverBackground.MotionEnabled`（默认 true）由宿主按
`MainWindow.NowPlayingMotionEnabled = ShowNowPlaying && AppState.DynamicBackground` 绑定。
停是**隐式**的、重开必须显式 `TryStartMotion()`，与 `ProgressRenderAnimator` 同一套约定
（`StopMotion()` 要复位 `_motionStarted` / bump `_motionGeneration`，漏掉就变单向开关）。

验收：首页门控 **1.00%** vs 强制开漂移 **8.16%** ⇒ 省 **+7.16% GPU / CPU 25.01% → 2.70%**；
漂移核对 ±0.06%（小于它的差异不算结论）。

另一个实测（2026-09-21 重测并修复）：歌词面板曾值 **+8.6% GPU**（`歌词·默认` 14.6% vs
详情页·默认 4.7%），而其中 **+7.9% 只来自当前句那一行**的 `BlurEffect Radius="0"` ——
半径 0 视觉上等于没有模糊，却强制该行走离屏管线。已修（`LyricView.axaml` 的 `:selected`
样式改成 `Effect="{x:Null}"`），歌词面板净代价降到 **+2.2%**。

| 项（1200x720，同轮消融） | GPU 净代价 |
|---|---|
| 当前句那行挂 `BlurEffect`（半径 0 **或** 1.5，一样贵） | **+7.9%** |
| 色团**漂移动画** | +4.27% |
| 封面色团层**画出来** | +1.57% |
| 另外 4 行歌词模糊（半径 1~2.5，above/below1/below2） | +1.27% |
| 两个进度 RAF 循环 | +0.07% |
| 漂移全停时整个歌词面板（含模糊） | **+0.06%** |

修复的验收（同轮 A/B，唯一变量就是当前句那一个 Effect，跨三次独立运行复现）：
GPU **14.86% → 6.93%**（省 +7.92%）、CPU 单核 **51.0% → 28.6%**；
抓屏确认像素差 **0.00%**（与噪声底同档 ⇒ 视觉零变化）。

⚠ **别把它读成"半径 0 走了特殊路径"**：给当前句换成半径 1.5 的真模糊，一样是 15.34%。
真正的变量是**那一行每帧都在变**（字号最大、被滚动定位、有缩放过渡）⇒ 它的离屏层每帧都要重建；
其余 4 行内容静止、层可复用，所以才值 1.27%。**"每帧在变" × "挂了 Effect" 才是代价公式**，
这也解释了为什么漂移全停时整块歌词面板只值 +0.06%。

### ⚠️ 同一处改动的收益随**窗口尺寸**变化 —— 小窗口的结论不能外推

上面两张表都是 1200×720 量的。同一份代码换到 **1920×1080**（用户的实际窗口，同日复测）：

| 项（同轮消融） | 1200×720 | 1920×1080 |
|---|---|---|
| `歌词·默认`（修复后） | 6.93% | **17.1~17.4%** |
| **当前句那条 `BlurEffect Radius="0"`** | **+7.92%** | **+0.7~0.8%** |
| 歌词逐行 `BlurEffect` | +1.27%（4 行带模糊） | **+2.8~4.5%**（11 行带模糊） |
| 色团**漂移动画** | +4.27% | **+4.2~8.1%** |
| 色团层**画出来** | +1.57% | **+0.85%**（位置平衡复测；全量矩阵那几轮读到 +2.0~3.7%，含位置偏差） |
| 两个进度 RAF 循环 | +0.07% | +0.06~0.22% |

⇒ 小窗口下"当前句那一行"压倒性地贵；大窗口下反而是**色团漂移**和**每一行的模糊**占大头。
**同一个改动在两边收益差 10 倍。** 探针必须用 `ALY_NP_SIZE=WxH` 对齐用户真实窗口再下结论。

⚠ 1920×1080 下的绝对值更容易被**外部 GPU 占用**整体抬高：同一档"漂移全停"的基线实测在
**0.62% 与 3.9% 之间跳**（同一台机器、同一构建）。判读前先看两个自证行 ——
`首页·对照` 与 `详情页·关动态背景设置` 都该落在 **0.6~0.8%**；明显更高就说明本轮有干扰，
这时只能看**同轮 A/B 的差值**，绝对值全部作废（受干扰那轮里"漂移全停时歌词面板净代价"
甚至算出负值）。

### 试过但没用的高性能画法：`CacheMode="BitmapCache"`

官方文档把它列为"渲染昂贵但很少变化的视觉"的正解。在本场景实测两极分化：

| 挂在哪 | 结果 |
|---|---|
| 歌词行（内容静止，只有滚动位置在变） | 同轮 A/B **省 2.97~4.46% GPU** —— 但**有副作用，已撤回**（见下） |
| 色团那 10 个全屏径向渐变椭圆 | 只省 **+0.15~0.53%**（噪声内）⇒ 无效 |

- **色团为什么无效**：它的代价不在"渐变计算"，而在"**全屏填充率 × 10 层半透明混合**"。
  栅格化成位图之后照样要全屏填一遍、照样要混合 ⇒ 缓存无从省起。同一结论后来用更硬的
  位置平衡 A/B 复核过（见下一条）：色团层**画出来总共只值 0.85%**，任何"换填充方式"的
  改动都不可能超过这个上界。
- **歌词行为什么撤回**：挂上缓存后再改 `Effect` **不再反映到画面** —— 把每行 `Effect` 置空后
  抓屏像素差 **0.00%**（没挂缓存时同一操作是 **5.68%**）。歌词行的模糊正是靠 class 切换
  （`above`/`below1`/`below2`）驱动的，缓存会把模糊状态**冻在第一次栅格化那一刻**。
  ⇒ 缓存类优化必须先问"这个视觉的属性之后还会不会变"；细节见 `docs/avalonia-tips.md`。

### 试过但没用的高性能画法：色团径向渐变 → 预渲染位图（2026-09-21）

思路：色团一直漂移、整层每帧重画，那就把它那条径向渐变**预渲染成 256² 位图**用 `ImageBrush`
铺上，每帧只采纹理、不再求值渐变。（与 `BitmapCache` 的区别：**换填充方式**而不是加一步栅格化。）

| 项（1920×1080，位置平衡 A/B，6 vs 6 行） | GPU | 组内极差 |
|---|---|---|
| 渐变填充（现状） | 12.26% | 0.49 |
| 位图填充 | 12.03% | 0.33 |
| **差** | **0.23%（小于极差）⇒ 无效** | |
| 整个色团层**不画**（同轮标尺） | 11.17% ⇒ 层本身只值 **0.85%** | |

- **为什么必然无效**：这一层"画什么"总共只值 0.85%（栅格化、混合、填充方式全在里面），
  **任何单项改动的收益上限就是它**。换填充方式最多吃到其中一部分 —— 实测 0.23%，在噪声内。
- 视觉上确实是零变化（平均通道差 **0.60 级**，阈值 3 下 0.00% 像素有差异；同轮对照
  "渐变改纯色"是 4.72 级 / 48.65%，说明判据本身灵敏）。**零变化也没用** —— 没收益就别加那 10 张纹理。
- 同类无效：停掉 `CrossFade` 里隐藏层那 5 个椭圆的漂移 **-0.25%**（≈0）；整层 `BitmapCache`
  **-0.5~0.6%**（更贵）。**色团这条路已经走到头，唯一的杠杆是"动"**（见第二节：漂移值 8~11%）。

### ❌ 试过但判负的改法：把漂移的驱动从组合动画换成定时器（2026-09-21，已回退）

**读数上真的省了，代价是画面肉眼可见地卡。** 这是"省 GPU"这条路上最容易踩的坑。

`AlbumCoverBackground` 原来用 20 条 `Vector3DKeyFrameAnimation`（10 个椭圆 × Translation+Scale）
驱动漂移，合成器按显示刷新率持续出帧；换成 **33ms 的 `DispatcherTimer` 直接写
`visual.Translation/Scale`**（关键帧、缓动、轨迹**一个字没改**）之后，同轮拉丁方量到：

| 项（1920×1080，拉丁方，同轮；六轮实测范围） | GPU | CPU(单核) | 实测更新率 |
|---|---|---|---|
| 组合动画（生产原状，也是**回退后的现状**） | **7.46~12.06%** | 20.2~36.7% | 按显示刷新率 |
| 33ms 定时器 | **0.92~2.31%** | 3.6~5.7% | **12.5~14.0 次/秒** |
| 漂移整个关掉 | 0.50~1.59% | 1.0~4.2% | — |
| 详情页主画布整块不画（漂移照开） | **+0.11~0.14%** | — | — |

⇒ 同轮配对差 +6.5 ~ +10.2 点 GPU、CPU 少 18~31 点（最干净的一轮："原组合动画 7.38%
vs 定时器 1.64% = +5.74%"）。**但用户直接反馈"背景变化卡卡的"，已 `git checkout` 回退。**

**回退后复测**（`artifacts/np_gpu_revert3.log`，4 变体 × 4 位置，1920×1080，**状态体检 16/16 通过**）：

| 项 | GPU | 极差 | CPU(单核) |
|---|---|---|---|
| 组合动画（现状） | **8.53%** | — | ~27% |
| 33ms 定时器（被否决档） | **0.98%** | 0.29 | 2.82% |
| 详情页主画布整块不画（漂移照开） | 8.16% | 0.39 | 24.71% |
| 漂移全停 | **0.63%**（逐行 0.65/0.65/0.69/0.51） | 0.19 | 1.93% |

⇒ 漂移本身 ≈ **+7.9% GPU**；换定时器省 7.55 点，**那 7.55 点就是用户丢掉的流畅度**。
同一轮自证：生产驱动（组合动画）帧节奏 **6.1ms(165fps)** —— 它由合成器按显示刷新率推帧；
被否决档实测 **14.2 次/秒**。**"页面内容"那一项只值 -0.37%**，再次说明钱只跟出帧次数走。

**为什么必然卡**（两条独立的物理原因，不是审美问题）：

1. 那台定时器的实际节拍只有 **12.5~14 次/秒**（名义 33ms 不是实际值）。
2. 相位取自 **15.6ms 分辨率**的 `Environment.TickCount64` ⇒ 位置被量化成阶梯，
   速度一顿一顿。低帧率还要靠它做相位，等于把量化误差又放大一层。

⚠ **成本公式要改写**：不是"重绘次数 × 每帧搬的东西（第一项压倒第二项）"，而是
**代价 ≈ 出帧次数 × 每帧固定开销，与"每帧画什么"几乎无关**。两个方向的证据：

- 内容侧怎么改都不动：色团整层不画只值 **0.85%**、详情页主画布整块不画 **+0.11%**、
  "渐变→纯色 / 渐变→预渲染位图"全落在噪声内（见下面两条）。
- **换算到"每帧"两个驱动几乎持平**：组合动画 12.06%/75fps ≈ **0.16% GPU/帧**、
  定时器 1.86%/14 次 ≈ **0.13% GPU/帧**。

⇒ **"降频省 GPU" = "少出帧" = 直接拿流畅度换钱**。想流畅就得按刷新率出帧，想省就得卡，
**这条路上不可兼得**。而组合动画是**唯一不会被 UI 线程饿死**的驱动方式（它由合成器推帧；
定时器空载就只有 14 次/秒，真机播放中只会更差）—— 所以留它，要降这一层的钱只剩
"别在看不见的时候动"（`MotionEnabled` 门控，早已做）。

⚠ 顺带纠正一个量法：**别用名义间隔或秒表猜驱动的频率**，必须数"它自己推进了几次"。
`AlbumCoverBackground.DriftTickCount` 那个只读计数器已随回退删除；现在由探针里
**被否决档的复刻**（`ALY_NP_MODE=backdrop-ab` 里的 `AB·定时器33ms`）承担，报的是数出来的节拍。
两次"没变化"才是定位依据：间隔改 16ms 读数一模一样、优先级 `Render`→`Normal` 也还是
13.9 次/秒（`ALY_NP_DRIFT_PRIORITY` 就是为这个加的，见 `artifacts/np_gpu_driftprio.log`）。

✅ **"机制未定论"已结案（2026-09-21，同日晚些）**：卡点是 **UI 线程静息时长睡 ≈79ms，
而 `WM_TIMER` 打不破这次等待** —— 与间隔、优先级、内核定时器分辨率（进程本来就是 1ms）、
电源节流（EcoQoS）**全都无关**，这些每一项都做了同口径对照。所以"UI 线程驱动的定时器
在这台机器上快不起来"是**环境事实**，不是我们哪里写错了。但它**是可以绕过的**：
见 `avalonia-tips.md` 末尾《UI 线程静息时长睡 ~79ms…》，实现是
`Infrastructure/UiFramePacer`（进度条静息写入 **8.7 → 34 次/秒**，≥50ms 停顿 **101 → 0**）。

回归线：`artifacts/np_gpu_latin_final.log`（改之前的对照）、`np_gpu_driftrate.log`、
`np_gpu_driftprio.log`、`np_gpu_revert.log`（回退后重跑：`AB·默认` = 组合动画、
`AB·定时器33ms` = 被否决档）。

### ⚠️ 试过但没用的高性能画法：固定画布 + 预渲染纹理 + 单视觉纯平移（2026-09-21，判负）

思路（**就是原版 UWP 在 DWM 里的模型**）：既然色团一直漂移、整层每帧重画，那就把每层 5 个椭圆
烘成一张 **1000×1000 纹理**、用一个 `Image` 顶替，漂移改成"**单视觉、纯平移**"。
（`AlbumCoverBackground.axaml` 里 `Viewbox Stretch="Fill"` + 固定 1000×1000 画布已经在了，
所以这版只差"烘纹理 + 换驱动"。）

| 项（1920×1080，拉丁方，**同一个定时器驱动**） | GPU |
|---|---|
| 10 个椭圆（径向渐变，现状） | **1.64%** |
| 单纹理平移（每层 1 张 1000² 纹理） | **11.35%** |
| 差 | **+3.96% 更贵**（相对那轮默认 7.38%），CPU 还多 8.9 点 |

**同一个驱动（都 ~13Hz 定时器）下差 7 倍** ⇒ 贵的不是"谁在推"，是"每帧搬的是一整块 1000² 纹理
（还要按窗口放大 ~1.92×、双线性采样）"这件事本身，而不是"10 个渐变的求值"。
旁证：同类"单个色团径向渐变 → 256² `ImageBrush`"的单项只值 **0.23%**（见上一条），
说明"纹理采样 vs 渐变求值"这个单项**根本不贵** —— 差在两处的组合上，具体机制**未定论**。

⚠ 该档的抓屏自证（`LayerTextureSelfCheckAsync`）**不稳定**：首轮读到 0.57 级（= 同一张画），
复跑读到 4.39 级 / 严口径 64.48%（可能是两侧相位没对齐，也可能是替身没烘对，自证分不出来）。
**所以这一档的结论只按 GPU 读数看**（同驱动 1.64% vs 11.35%），不靠那条自证。
产物已 `git checkout` 撤回，只留探针档位（`BackdropAblation.LayerTexture`）当回归线。



### ⚠️ 消融矩阵有个会骗人的夹具：变体和"轮内位置"绑在一起

上一条的结论，前两轮量出了**符号相反**的结果：一轮说位图省 2.8%，另一轮说位图贵 1.4%，
而两轮各自的三次读数都稳到 ±0.1% —— **稳的假象比噪声更危险**。根因：
全量矩阵里每个变体只出现一次、位置固定，而**同轮读数本身带位置偏差**（第 1 行比第 2 行高约
1.4%，连续三轮都一样），于是"变体差"里混进了"位置差"。

**定稿做法：拉丁方**（`ALY_NP_MODE=backdrop-ab`，报告由 `ReportAbGroups` 出）。
N 个变体 × N 个位置，每个变体在每个位置上各坐一次（顺序 `orders[round][slot] = (slot + round) % N`），
位置偏差被**严格**抵消 ⇒ 可以直接报均值，均值差就是纯净的效应量。
`ALY_NP_ROUNDS=k` 只跑前 k 轮（冒烟用，位置偏差不再抵消，只看组内极差）。
历史做法"轮内奇偶反序 `A B A B / B A B A`"只能抵消一轮内的顺序效应，变体一多就成半吊子，已被取代。

四条配套规矩，写新消融时照做：

1. **变体不许和位置绑定**。单变量"一行一个"的全量矩阵里，**1% 级的差值不可信**
   （§二那两张表里 >3% 的结论仍成立）。
2. **每轮放一个"上界锚"**：把这一整块删除/隐藏的那一档也量出来（如「减色团」「藏页面内容」）。
   任何单项的收益都不可能超过锚，**超了就是夹具在骗人**。
   ⚠ 锚本身也依赖"漂移停没停"：同一个「关动态背景」在定时器默认那轮只值 **-0.27~-0.76%**，
   在组合动画当默认那轮值 **-6.54%** —— **锚不是一个固定数，它是"当前驱动频率"的函数**，
   引用时必须带上"漂移在什么状态下量的"。
3. **报差值时必须带上组内极差**。极差 0.33 的组里，"差 0.23" 等于没差；
   极差比自由度更能说明"这个差能不能信"。
4. **整轮末尾那几行会掉到 13~14fps**（帧节奏量到 70ms+），读数跟着失真 —— 实测末尾那一档
   「减色团」读到 4.68%，而同轮轮首的「默认」稳定在 8.7%（差的 4% 全是失真）。
   现在报告里有**帧节奏体检**，把 >30ms 的行点名出来，**这些行整行作废**，别拿去凑均值。
   ⚠ 但别把这条反过来用：**"掉帧诊断只对由 UI 线程推帧的档有效"** ——
   「旧组合动画」那几档即使帧节奏掉到 13fps，GPU 仍稳定在 12%（它的重绘由合成器自己推，
   与"UI 线程能不能按时回调"无关）。拿掉帧去否定一档读数前，先问它的帧是谁推的。

**复现（撤回后第二次独立验证）**：把产物改回渐变填充、重跑同一模式，得「默认(渐变) 8.70%
vs 位图填充 9.02% ⇒ +0.32%」。两次**互换了哪个是"现状"**、绝对值差了 3 个百分点（外部 GPU 负载），
但符号一致地落在噪声内 ⇒ 结论稳定：**换填充方式无效**。产物已 `git checkout` 撤回，
只留下探针与这份记录当回归线（`artifacts/np_gpu_backdrop_balanced.log` / `_reverted.log`）。

探针里对应 `ALY_NP_MODE=backdrop-ab`（`ALY_NP_SAMPLE` 可拉长采样窗口）。

### 像素判定的两级口径：`DiffRatio` 看"有没有画出来"，`MeanDelta` 看"是不是同一张画"

`DiffRatio` 带阈值（默认 24 级），只回答"有多少像素差得**明显**"。判"某效果有没有渲染"够用，
判"两种画法是不是同一张画"会失灵 —— 重采样误差每像素只差几级，全落在阈值下面，读数恒 **0.00%**，
什么也没证明。于是补了 `ScreenCapture.MeanDelta`（每像素最大通道差的**平均值**，连续量）并同时报
**阈值 3 的严口径**：

| 对照 | 阈值 24 | 阈值 3 | 平均通道差 |
|---|---|---|---|
| 位图填充 vs 渐变填充 | 0.00% | 0.00% | **0.60 级** |
| 渐变改纯色 | 0.04% | 48.65% | 4.72 级 |
| 少画 2 个色团 | 1.12% | 39.44% | 4.86 级 |

⇒ 判据：**1~2 级 = 重采样误差**（可用），**5 级以上 = 真的换了样子**。只有阈值 24 那一列时，
"0.00%" 会把这两类混成一句"视觉无变化"。

## 三、三类"一直在动"的机制，成本模型完全不同

别用 GPU 读数否定任一者：**最小化时窗口不 present，GPU 必然归零**。

| 机制 | 跑在哪 | 最小化时 | 门控做法 |
|---|---|---|---|
| 自续订 RAF 循环（`ProgressRenderAnimator`） | UI 线程 | **回调仍送达**，每帧照写 `ScaleX` | `ShouldAnimate()` 里加 `IsHostPresentable()`；停止隐式、恢复要显式 `RestartFrameLoop()`；`_lastPresentable` 防抖 |
| 框架主题动画（`ProgressBar IsIndeterminate=True`） | 合成 + UI 线程 | **照转**，净代价 **2.60%** 单核 | `Infrastructure/IndeterminateAnimationGate` 附加属性 `IsActive="True"` |
| 组合动画（`AlbumCoverBackground`） | 渲染线程、帧驱动 | 不渲染 ⇒ 0 成本 | 见第二节 |

- 判据统一为 `IsHostPresentable`：`TopLevel.IsVisible` && 非 `WindowState.Minimized`。
  ⚠ **最小化时 `Window.IsVisible` 仍是 `true`**，只看它必然漏掉最小化。项目里已有两处实现，别写第三套。
- 不确定进度条共 5 处已全部门控：`PlaylistView`（补页）、`AccountView`（刷新）、`SearchView`（搜索中）、
  `LoginDialogView` ×2。新增时别忘了挂。
- 门控**必须只"压"不"吃"**：记住 XAML/绑定**想要**的值（`Desired`），不可显示时压 false、可见时还原；
  压时打 `Suppressing` 标记，否则自己写的值会被变更通知误当成"绑定改了值"而覆盖 `Desired`。
  离开视觉树时也置 false，重新挂回时由 `Apply` 还原。

## 四、写性能探针的坑

- **消融场景要写成"完整状态"**，不是"在上一个场景上再关一样"，行与行才可任意比较。
- **变体不许和"轮内位置"绑定**（详见 §二末）：位置本身带 ~1.4% 偏差，绑在一起能读出相反的符号。
  定稿做法是**拉丁方**（`ALY_NP_ROUNDS` 控制跑几轮），1% 级的改动别拿全量矩阵的单行差值当结论。
- **每轮放一个上界锚**（把整块删掉那一档）：单项收益不可能超过它，超过就是夹具在骗人。
- **差值要连着组内极差一起报**：极差比自由度更能说明"这个差能不能信"。
- **别假设"名义参数 = 实际参数"，要数出来**：`DispatcherTimer(33ms)` 实测只有 12.5~14 次/秒，
  而改间隔（16ms）、改优先级（Render→Normal）都纹丝不动 —— 这两次"没变化"才是定位的依据。
  生产侧那个只给探针读的 `DriftTickCount` 已随驱动回退删掉；现在由 A/B 档里**复刻**那台定时器的
  `AB·定时器33ms` 承担（行里报的"驱动"一栏就是数出来的节拍）。
- **判定阈值要用"绝对下限 + 噪声底"两者的最大值，且口径要与结论匹配**：原来写
  `Math.Max(noise, 0.002) * 2`，噪声底从 0.00% 抖到 0.01% 就把阈值从 0.40% 拉到 0.02%（20 倍），
  同一组图从"视觉无差异"翻成"观感变了"；而且用带阈值 24 的口径去判柔光色团，本来就读不到东西。
  现改成 `Math.Max(max(两个口径的噪声底) * 2, 0.004)` + 严口径（阈值 3）判定。
- **每条自证都要写清"什么读数算通过、什么算作废"，并让日志自己喊出来**（别只打一个数字）：
  `LayerTextureSelfCheckAsync` 首轮 0.57 级（通过）、复跑 4.39 级 —— 后来者是"相位没对齐"
  还是"替身没烘对"，工具分不出来，所以它现在直接打印"这条自证作废"。
- **验收场景照应用自己的门控走**（读回控件状态再落实）。探针自己拨开关 ⇒ 应用改没改好都量出同一个数。
  ⚠ 反过来说：**A/B 夹具体必须自己去"落实 + 读回"驱动状态**，那是另一回事 —— 见下面那条状态体检。
- **帧节奏要在 GPU 采样之后量**（请求帧本身会驱动平台出帧）。
- **"某循环是否在跑"要读它写的成果**（`ScaleX` / 合成视觉 `Translation`），别数帧数或看进程 CPU。
- **`CompositionVisual.Translation` 的 getter 读基础值**，不反映组合动画推到服务端的当前值
  ⇒ 拿它判"还在不在动"是瞎的（实测 13 个场景全是 0.00px）。
- **夹具缓存的控件引用会失效**：控件被重建后，沿用旧快照会指向已脱离视觉树的实例 ⇒ 写上去纹丝不动。
  每次从视觉树重取；"原值"只能从活的、样式已生效的控件读。
- ⚠ **每格测前"落实"、测后"读回校验"驱动状态 —— 否则"没在动"会伪装成"省下一大截"**。
  背景：绕过控件直接对合成视觉 `StopAnimation`（收尾清理最容易这么写）**不改**控件内部的"已启动"标志，
  而它只在属性**变化**时动作 ⇒ 之后再也点不着火，且后面每一行的读数都跟着掉到地板。
  实测代价（2026-09-21 回退那轮）：同一档"照应用自己的样子"在一轮里读出 **0.58% / 8.51% / 8.51% / 0.72%**。
  现在收口成两条：① 停/起一律走 `MotionEnabled`，纠正必须是一次真转换 `false→true`；
  ② 每格读完 `AlbumCoverBackground.IsDriftRunning`（只给探针读）与标签期望比对，
  不一致就在日志里喊、并进报告的**状态体检**。只在 `ALY_NP_MODE=backdrop-ab` 里做，
  全量验收档必须袖手旁观（否则量的就是探针而不是应用）。
- 真窗口可见时 CPU 大头**不是**这些循环：可见时进程 CPU **20~28% 单核**（Acrylic 模糊层 + 全窗合成），
  循环开/关配对差只有 ±1%（噪声内）。**要降可见时 CPU，方向不在这里。**
- **自测/探针进程里 `DispatcherService.Post` 的事件永远不跑**（依赖 Avalonia UI 泵，无人泵）。
  播放器事件断言两条路：① 无头 Stub 的事件是同步 raise，直接断言（首选）；② 真机进程要么泵
  `Dispatcher.UIThread.RunJobs` 循环、要么只做属性轮询——但**事件转发链必须有一条同步路径覆盖**，
  否则会漏掉"包装类构造时没接线"这类 bug（2026-09-17 CrossfadeAudioPlayer 漏 Wire primary：
  手动切歌走属性读所以有交叉，自然播完靠事件所以全哑）。
- **"手动路径好使、自动路径哑"优先查两条路径的依赖差异**：属性直读 vs 事件推送——分叉点就是嫌疑点。
- **`.ps1` 里的中文必须写 UTF-8 BOM**（`[IO.File]::WriteAllText($p,$t,(New-Object System.Text.UTF8Encoding($true)))`）。
  Windows PowerShell 5.1 对无 BOM 的 .ps1 按 GBK 解码：UTF-8 的"秒"（`E7 A7 92`）尾字节会和紧随的
  `'` 组成一个 GBK 字，**把字符串的结束引号吃掉** ⇒ 报一堆 `意外的标记` / `缺少右"）"`。
  `scripts/*.ps1` 两份都已带 BOM（2026-09-17 补）。

## 五、歌单页"什么都不做也有 CPU"：先证明它是不是真的，再谈归因

用户报告"在歌单页什么都不做也有 CPU 占用"。用 `--pl-cpu-real`（真窗口 + 真 `PlaylistView` + 真 VM）
做**跨构建同口径对照**（`c7542b3` = 该报告之前的最后一次应用改动，用 `git archive` 抽到临时目录另构建）：

| 场景（可见） | c7542b3 | HEAD 各次 | 判读 |
|---|---|---|---|
| 空页（无内容） | 0.00 / 0.78 | 0.00 / 0.26 / 0.78 | 平台静息，≈0 |
| 歌单页·顶部 | 0.00 / 3.91 | 0.78 / 3.90 / 8.33 / 9.11 | **同一构建跨次 0 → 9%** |
| 歌单页·底部 | 4.94 / 14.31 | 0.00 / 3.38 / 7.81 / 9.37 / 12.75 | **同一构建跨次 0 → 13%** |
| 歌单页·近底（不补页） | 0.00 | 0.00 / 0.00 | 两次都是 0 |
| 最小化 / 页面隐藏 | 0.00 | 0.00 | 门控有效 |

⇒ **可见页面那一栏的读数是 0~14% 的随机跳**，单个数字不能当结论，也**不足以支撑"某个提交让它变贵了"**
（两个构建的分布重叠）。要下结论只能靠**同一次运行内的配对/消融**（如"绕过门控"那条同轮 A/B）。

在同一态上把"到底在不在变"直接量出来（静止 2 秒）：

- `ScrollChanged` **0 次**（没有"自己滚自己"的自激）；
- `offset / extent / ScrollBarMaximum / 实化行 / 视觉节点` 全部 **Δ0**（没有布局漂移）；
- 两帧像素差 **0.0000**（画面完全一致）；
- `GC 0/1/2 = +0`，分配 = **0.6MB/6s** —— 与"空页"那一档完全相同，这 0.6MB 只是
  `DrainAsync` 里 `Task.Delay(5)` 的自身开销（≈200 次/秒）。

⇒ 真静下来的时候，歌单页是**零成本**的。中间出现的几 % 是**场景切换的尾巴**（容器实化、封面防抖、
布局落位）与机器噪声，不是持续占用。**拿这个探针去证明"空闲占用"是测不出来的 —— 要么把场景切走之后
再等更久，要么去真实进程上量（见 `scripts/cpuwatch.ps1`）。**

`scripts/cpuwatch.ps1`（新）：从外部按间隔采样真实应用的 CPU，并**按线程**列 top-N 归因
（UI 线程 ⇒ 每帧 UI 工作；渲染/合成线程 ⇒ 真在出帧；线程池 ⇒ 后台循环）。
口径提醒写进脚本头：它报的是**单核百分比**，任务管理器是**全机百分比**（差一个逻辑核数），两边不可直接比；
另外窗口被遮挡/最小化时合成器不出帧，CPU 自然归零 —— 采样期间必须让窗口可见且未被遮挡。

### 6.1 上一节的"零成本"只对"从没动过的提示条"成立

真静下来是零成本的结论**有一个前提**：那条补页提示条此前**从未实化/从未动过**。
一旦它显示过一次，`IsVisible=false` 并不会停掉框架动画 —— 于是"什么都不做"也会一直有占用，
直到**离开该页**（控件脱离视觉树）才归零。这正好对得上用户"歌单页有、首页没有、离开就没了"的描述。

### 6.2 四态配对实测（`--idle-cpu-real` + `ALY_IDLE_DWELL=bar-ab`）

同进程、同一份数据（300 行）、同一次驻留，四种状态**循环**采样，每态两个 8s 窗口
（跨进程/跨时段的对比会被本机 ±1% 单核的抖动淹没，配对是唯一能把差值提出来的做法）：

| 档 | 提示条实测 | CPU%单核 | 任务管理器口径 | 分配/8s | 活动线程 |
|---|---|---|---|---|---|
| 隐藏 + 强开动画（旧行为） | 被隐藏，**动画=开** | **6.18%** | 0.39% | 8.3MB | 固定线程 2.71% + 渲染 1.74% + UI 1.55% |
| 可见 + 动画 | 有效可见，动画=开 | **6.38% / 5.80%** | 0.36% / 0.40% | 7.1–7.2MB | 固定线程 ~3.1% + UI ~2.7% |
| 可见 + 无动画 | 有效可见，**动画=关** | **0.96% / 0.58%** | 0.06% / 0.04% | 3.1MB | UI 0.4–0.8% |
| 隐藏（真实应用做法：只翻 `IsLoadingMore`） | 被隐藏，动画=关 | **0.00% / 0.39%** | 0.00% / 0.02% | 3.1MB | 无活动线程 / UI 0.58% |

读法：
- **成本在"动画在转"，不在"控件在树上"**：隐藏态 6.18% vs 隐藏+动画关 0.39%；可见态 6.38% vs 0.96%。
- **分配量是同一指纹**：动画开 7~8MB/8s（每帧都在分配），动画关 3.1MB/8s（= 探针自身的
  `DrainAsync(Task.Delay(5))` 底噪）。看分配比看 CPU 更不容易被机器噪声骗。
- GPU 全程 ≈0.00%（峰 0.14%）⇒ 这条成本**不是**"在出帧"，是动画时钟 + 该帧的失效/重绘。

### 6.3 修法与验收

`Infrastructure/IndeterminateAnimationGate` 的判据补上"控件自己是否被有效显示"
（`bar.IsEffectivelyVisible`），触发用**自身 + 全部可见祖先的 `IsVisibleProperty`** 订阅
（`Visual.IsEffectivelyVisibleProperty` 在 Avalonia 12 不是公开成员，订阅不到）。

验收用最硬的一对（`ALY_IDLE_DWELL=bar-onoff`：**可见+动画 → 只翻业务标志隐藏**，
后一档刻意**完全不碰** `IsIndeterminate`，所以"动画=关"只可能是门控写的）：

| 对 | 可见+动画 | 只翻业务标志隐藏 | 提示条实测 |
|---|---|---|---|
| 1 | 8.31%（0.52%） | **0.58%**（0.04%） | 隐藏态 `动画=关`（门控写的），分配 7.1→3.1MB/8s |
| 2 | 4.64%（0.29%） | **0.39%**（0.02%） | 同上 |
| 3 | 5.41%（0.34%） | **0.19%**（0.01%） | 同上 |
| 4 | 2.52%（0.16%） | **0.19%**（0.01%） | 同上 |

（括号内为任务管理器口径 = 单核% ÷ 16 逻辑核）

⇒ 四对全部复现同一结论：**可见时照常转（2.5~8.3%），隐藏后门控把动画按下（0.19~0.58%）**。
对照修前：同一动作留下的是 2.71~3.48%（只隐藏）或 4.83~6.18%（隐藏且动画未停）
—— **只压"空转"，不动业务语义**。

**这就是"歌单页什么都不做也有 CPU"的答案：不是歌单页本身，是那条 3px 提示条的框架动画
在隐藏后继续空转**（占比 ≈0.3% 任务管理器口径，不衰减，直到离开该页）。

### 6.4 顺带纠正两个测法

- `--pl-cpu-real` 的静止判定（`ScrollChanged=0` / 像素差 0.0000 / GC +0）**证明不了这条**：
  动画在转时这些指标**全都是 0**（动画只改它自己的 transform，不改 offset、不产生像素差、
  也不分配在 GC 计数上），而 CPU 是 6.18%。⇒ 静止类指标只能否掉"自激滚动/布局漂移"，
  不能否掉"动画空转"。
- **探针永远测不到"用户手滑出来的状态"**：它不会发滚轮事件、也不会点开歌单。
  想量"打开过歌单之后一直有占用"，必须能在**同一进程内**把该中间态构造出来
  （本节的四态档就是这么做的），否则只能在真实进程上用 `scripts/cpuwatch.ps1` 量。
